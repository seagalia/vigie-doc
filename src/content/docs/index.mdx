## The problem

A load balancer or a proxy needs the list of endpoints behind each service, and that list lives in many places, such as
DNS,
Consul, the pods behind a Kubernetes Service, a text file kept by hand, or an inventory served over HTTP. Teaching each
client every one of those sources means as many integrations to write and
to keep working.

## What Vigie does

Vigie reads the endpoints of each service from one source and serves them all the same way. A client asks for a service
by name with `GET /services?service_name=<name>` and gets a JSON list of endpoints, each an IP address and a port with
its
weight, whatever the source behind it.

```console
$ curl -s 'http://127.0.0.1:8080/services?service_name=web'
[
  { "ip": "10.0.0.5", "port": 8080, "load_balancing_weight": 0 },
  { "ip": "10.0.0.7", "port": 8080, "load_balancing_weight": 3 }
]
```

The same endpoints come over gRPC too, see [the EDS service](/reference/http-api/#the-eds-service).

## Who uses it

Vigie is built as the endpoint source of [Flock](https://github.com/seagalia/flock) and meridian. The Flock agents poll
it for the endpoints of their backends with the [`eds` block of a backend](/guides/feed-flock-backends/), and meridian
reads the same answer. Any other client that can send an HTTP request and parse JSON can do the same.

## Status

Vigie is released under the [MIT license](https://github.com/seagalia/vigie/blob/main/LICENSE.txt) and hasn't reached
1.0 yet, see [Download](/download/) for the latest release. The answer of `GET /services` is a contract with its clients
and stays as it is, while the configuration file can still change before 1.0.
